# Durable tasks and routing

Pace assigns `single`, `scout`, `plan`, or `scout_plan` to the active task. Ordinary continuation retains its stage and lead model/effort. A completed scout report is saved before completion or planning begins. Correcting a plan continues the planner. Vex can explicitly choose to reroute, replan, replace the task, ask for clarification, or answer an independent question separately. Confidence and probabilities are diagnostics; they do not trigger routing thresholds. Message length, keywords, sentiment, and correction counts do not classify these actions.

Vex uses the existing validated `vex_choose` contract. A separate choice assesses recorded evidence as `closed`, `partial`, or `unknown` after the technical result is persisted. A completed Codex invocation, scout report, or saved plan does not establish completion of an implementation. Activity results, agent task events, answers, and artifact references are collected in core for terminal UI, exec, and Remote. The ordinary answer is retained as evidence, with its coverage and remaining work; Pace does not invent a remaining-work note from a forced-choice response. No extra model status-note call is made when that answer supplies the evidence. Unavailable assessment leaves completion unknown.

Control and completion-assessment contexts have a 24,000-byte serialized JSON budget. Assessment sends the current observations once. Oversized contexts use marked excerpts of text and arrays, retaining both the beginning and end when possible. The request reports omissions and instructs Vex to choose `unknown` when required completion evidence is omitted. Full observations remain in the durable session. This byte budget is a conservative input bound, not a provider tokenizer or a guarantee of assessment accuracy. Vex classifies supplied evidence; it does not independently run tests or audit files. Known provider token-limit errors are shown without exposing the raw provider response.

## Explicit control

- `/manual` selects an allowed workflow or route. Explicit selections are recorded as user actions. Delegating a stage to Vex uses the same editable profiles as automatic routing. Scouts, verifiers, and side answers can use any enabled permitted route; Luna is not required.
- `/execute [plan-file] [instructions]` reads the current complete plan and creates a fresh normal execution session. The session records the source task, session, artifact/path, and exact plan. UI and Remote use the same service. A queued operation keeps its identity when an execution session is created, allowing restart to find that session instead of creating another one.
- `/btw <question>` asks a read-only agent in a separate thread. Vex selects its route and reasoning depth. Its labelled snapshot includes retained exchanges and selected observations, not the complete tool history. The answer records its author and source attempt; the main task, route, thread, tasks, checkpoint, and context measurement retain their ownership.
- `/adopt <side-answer-id>` explicitly transfers one selected finding to the main task. Vex can also recognize such a request and select the source with a separate choice. Other side answers are not automatically replayed to the lead agent.
- `/verify` and verifier follow-ups have separate thread, route, tasks, context, and turn count. They do not generate the main checkpoint. Accepted plan revisions return to the planner.

An exec invocation that needs workflow clarification prints the request and exits with status 2. Approvals and interactive tool questions are handled explicitly by its existing noninteractive policy.

## Persistence and recovery

Every model stage has a durable attempt identifier and role. Start is saved before inference; each new thread ID is saved immediately, and progress observations are checkpointed every two seconds while the stage runs. Terminal result, error, or cancellation is saved before a following stage starts. On load, a running record with no live owner is marked failed with an interruption note, completion remains unknown, and the saved thread plus observations are retained so the next user turn can continue without a manual recovery command.

The session store serializes updates against the latest persisted revision within the Pace process, including independent store instances. Whole stale snapshots are rejected. Tracked snapshots reapply only their concrete changes; edits to the same value conflict instead of silently overwriting it. Main and auxiliary writes preserve independent attempt and side-result records in either order. This is not a cross-process database lock: separate Pace processes writing the same session are outside that guarantee.

Queued saves capture a shared caller's state and baseline after earlier writes finish. Turn history merges independent appends and edits to different fields of retained turns, including UI activities and steering history, while retaining the 20-turn window. JSON-omitted optional fields do not count as edits. Refreshing a caller after I/O rebases mutations made during the write so the next save does not delete unseen auxiliary records.

If a terminal UI turn encounters genuinely incompatible changes, Pace pauses queue draining, preserves its rejected snapshot under the conversation's `recovery/<uuid>.json`, and reloads the saved conversation. The UI reports recovery and accepts the next prompt without restarting Pace. It does not automatically repeat an invocation whose work may already have completed. Mandatory writes still stop execution on storage failures; when storage becomes available, a new prompt can continue in the same process. Recovery requires both retaining the rejected snapshot and reading the saved conversation successfully.

Explicit workflow, model/effort, and auto-routing selections apply their intent to the latest session inside the store's update queue. They do not save an entire UI snapshot: a shallow display copy can retain an old revision while sharing task objects that execution has already changed. Each manual workflow choice increments the latest generation and retains the attempt ledger and prior decisions. Routing changes wait for active execution, verification, checkpoint, or compaction to finish; an independent title attempt does not block them. Terminal UI and Remote use the same operation and publish the saved snapshot after success.

Queue entries retain operation ID, text, intent, target session/task, role, and optional side source. They are acknowledged after success. Failures pause draining; unstarted operations can resume after restart, and orphaned running attempts are automatically recorded as interrupted when the session loads. Old string entries become ordinary prompts with stable IDs, without interpreting command-looking text as a stored intent. Undo, deletion, and file restoration invalidate context and task assessment; the cost ledger survives visible-history truncation and undo.

Older sessions remain readable. Their workflow is unknown until Vex receives the retained evidence. A missing workflow does not establish that a scout needs to run again. Manually edited routing text is preserved; absent new sections receive defaults.

## Usage and audit

Saved control decisions link to task, stage, role, attempt, and context action. They distinguish user selections, Vex choices, retained routes, and selected side results. Pace does not invent a natural-language explanation from probabilities.

`/stats` uses the durable Codex attempt ledger, including errors, cancellations, scout format repairs, checkpoints, and manual compaction. It reports known subtotal separately from full cost. Missing billing fields, unidentified usage, backend rerouting without billable attribution, unknown prices, and compaction placeholders leave full cost unknown. Legacy history without an attempt ledger also leaves full historical cost unknown. Context occupancy is a separate measurement.

Usage is correlated by Codex thread and turn IDs, including notifications received before the `turn/start` RPC response. Per-request cumulative readings are deduplicated within the identified turn. Each attempt retains its source route and price snapshot; later route changes do not reprice earlier tokens. Ordinary, cached, cache-write, and output tokens have separate rates. Reasoning output is already included in output. These are Standard API estimates, not measurements of Codex subscription allowance. Vex call latency is reported separately; its choice contract does not expose token usage or billed cost.

## Context policy and evidence limits

This change adds no automatic context strategy controller, fresh replay, or new compaction policy. Changing model or effort continues the existing thread. Existing checkpoint triggers remain 16 turns or 75% measured context; authorship remains the main session route. Auxiliary roles cannot replace that route or trigger its checkpoint.

The fresh-completion benchmark does not validate checkpoint thresholds, authorship, Vex profiles or routing quality. Production context policy remains unchanged; stable leadership alone does not establish quality or savings.

Deferred questions: behavior near the context limit with rich tool history, costs beyond two subsequent turns, complete native compaction cost, and fidelity across checkpoint authors. Any new automatic migration or authorship policy needs separate evidence and user decision. Those studies are outside this routing change.

## Durable steering and decision projections

Accepted queue steering is recorded independently of turn history in `steeringRecords` (schema version 1). Its ID is the queued operation ID, with session/task, UI turn key, agent role and available attempt/thread IDs. Pace saves `pending` before trying delivery, then saves `unknown` before the runner call, and saves `delivered` before acknowledging the queue or reporting success in the UI. The runner has no idempotency key. A rejected call may have reached Codex, so an ambiguous send or delivery-save failure stays `unknown`; it is neither automatically resent nor executed as a new task. A failed initial pending save is known unsent and can be explicitly retried. A failed write-ahead save blocks delivery. On load, delivered operation IDs are removed from the queue projection; uncertain operations remain paused. To resolve uncertainty, inspect the recorded delivery and Codex thread, then deliberately delete/edit the queued item or submit a new message. Editing creates a new operation; this is a user decision, not proof of exactly-once delivery.

Raw steering stays with the active Codex agent and the session audit. It does not update the task brief or become another task. Fresh replay without a thread includes delivered instructions for the current task and role, deduplicates IDs already linked to retained turn history, and excludes uncertain, unrelated and explicitly removed instructions. Undo/delete/rewind mark linked instructions inactive while retaining their audit records; redo restores their applicability. A checkpoint handoff also carries applicable delivered steering when it starts a fresh thread. Legacy turn steering remains readable, without inventing missing task/role attribution.

Every `vex_choose` call passes through `projectVexRequest` at `VexRouter.choose`, including workflow, stage, side route, control, assessment and inline `adopt_side` source selection. The audited decision path uses the same idempotent projection. The budget measures serialized UTF-8 JSON for `{name, arguments}`: 22,000 bytes, leaving 2,000 bytes of the 24,000-byte local allowance for MCP envelope overhead. This is not a provider token limit. Under-budget tool requests are passed through unchanged. Existing factory selection of recent conversation excerpts remains compatible; `originalBytes` describes the actual request presented to the shared boundary, not all session history.

Oversized projections preserve the question, options, request constraints, current request, explicit task criteria/constraints/instructions, and task stage. They compact optional results, deduplicate repeated entries and prefer recent evidence over history/handoffs. Large activity details become bounded first/last-line excerpts, with full records retained in the session. Projection metadata reports original/final tool-payload bytes, omitted data classes and possible evidence omissions. A minimal reference projection handles pathological optional data; if protected inputs still cannot fit, Pace returns a controlled local error without a provider call. No projection mutates persisted session data. Operational steering is never copied into these requests. Pace has no semantic steering-to-task-state adapter: only already explicit task fields can influence Vex; there is no keyword classifier, rewriting prompt or additional model call.

## Assessment and provenance contract

New attempts snapshot their explicit criteria. Without separate criteria, Pace preserves the recorded goal verbatim as one required goal criterion; it does not infer a checklist. Version 1 assessments retain the UI enum `closed`/`partial`/`unknown`, Vex's proposed enum, criterion statuses, missing information, uncertainty, and an evidence catalog. Catalog IDs identify actual attempt observations by attempt ID and observation index, with source kind and artifact paths where recorded. Session validation rejects unknown evidence IDs, mismatched sources/paths, missing snapshot criteria and unsupported closure. Agent declarations remain reported observations, not independently verified tests.

The installed `@sidearker/vex-mcp` `vex_choose` routing contract (`contractVersion: "1"`) returns only a choice, abstention flag, confidence and probabilities. It has no criterion-status/evidence-reference result contract. Consequently new criterion rows are explicitly unknown with empty evidence links. A proposed `closed` becomes `unknown`; a proposed `partial` can remain a limited `partial`, and potentially necessary omitted evidence forces `unknown`. The proposed decision stays in the audit. Pace cannot safely produce positively verified criterion coverage with this external contract; adding arbitrary response fields would not repair it. Legacy enum-only assessments remain readable.

New Vex decisions store a canonical SHA-256 fingerprint of the parsed effective prompt config (defaults plus preserved user overrides), along with schema version and a separate semantic profile ID/version. Key ordering does not affect the fingerprint. An absent legacy fingerprint means `unknown`. Fresh-completion manifests retain the exact effective prompts and source/configuration hashes. Decisions also retain aggregate `durationMs` and per-attempt duration, success/error status and retry flag, including invalid responses. Local budget rejection records zero provider requests. `usage` and `costUsd` are explicitly `unknown`: the routing decision contract supplies no reliable request-attributed billing. Call counts are never converted into free usage or cost.


Scout reports preserve all validated findings, inspected coverage and explicit gaps without a count/character truncation. The completion agent starts from this evidence, verifies critical claims and reads further to close gaps or implement/test. The saved per-turn handoff is available through Ctrl+O after reload, including failed and resumed turns. Scout input includes available skill guidance for requested reading/app inspection; unavailable tools must be reported as a gap.

Routine continuation still runs task control and records its decision, while preserving workflow/route without repeat workflow-selection messages. Workflow descriptions include positive and negative examples; code review requires a capable reviewer. `/debug [turn]` separates the Vex decision trace from Pace-added prompt sections and the actual Codex `turn/start` input. It is local, read-only and redacted.
